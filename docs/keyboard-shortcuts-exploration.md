# 快捷键探索记录

本项目曾探索为桌面窗口提供 `Ctrl+R`、`Ctrl+,` 和 `Ctrl+N`。该功能未被采用；本记录保留已验证的技术边界，供以后重新评估输入方案时参考。

## iframe 焦点边界

DSH Web UI 通过 HTTP 或 HTTPS URL 运行在 iframe 中，与 DSH Desktop 顶层页面不是同源页面。焦点位于标题栏或顶层页面时，Vue 的捕获阶段 `keydown` 监听器可以识别快捷键；焦点进入 DSH iframe 后，键盘事件仅在 iframe 文档中传播，不会传递到父页面。

因此，顶层 Vue 页面不能在不修改 DSH 页面或改变其承载方式的前提下，为 DSH 内容区实现窗口级快捷键。

## 原生全局快捷键

曾使用 Tauri 的全局快捷键插件注册三个组合键。Linux 实际运行中，按下任一组合键都会使 DSH Desktop 被系统判定为无响应。将注册和处理逻辑移出主线程后，问题仍然存在。

全局快捷键还会在应用失焦时与其他程序竞争组合键，不符合仅在 DSH Desktop 窗口中生效的预期。当前不使用这一机制。

## 隐藏菜单栏的加速键

曾为每个窗口创建原生菜单项，配置加速键后隐藏菜单栏。该方案不会导致窗口卡死，但在当前 Linux WebView 环境中，焦点位于 DSH iframe 时不会触发对应动作。当前不使用这一机制。

## Host 反向代理的可能性

Host 可以将 iframe 请求转发到 DSH，使 DSH 页面经由应用控制的地址加载。代理还可以向页面注入键盘桥接脚本，由脚本通过 `postMessage` 将快捷键动作通知顶层页面。

该方案会新增静态资源、重定向、Cookie、流式响应、WebSocket、安全边界和上游兼容性的维护责任。若以后决定采用，应单独设计代理来源、消息校验和 DSH 契约测试，而不是把它作为简单的 URL 转发。

## 结论

当前版本不提供 DSH Desktop 自有的窗口快捷键。标题栏按钮和设置界面继续作为窗口操作入口。
